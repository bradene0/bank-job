# Data model (PostgreSQL)

The schema lives in Flyway migrations (`services/game-api/src/main/resources/db/migration`);
this page explains it. Hibernate runs with `ddl-auto: validate`, so the entities and the
migrations cannot drift apart silently. All money is `bigint` cents; never floating point.
Ids are UUIDv7 (time-ordered), generated by Hibernate or by PostgreSQL 18's `uuidv7()`.

## Sessions and the per-session branch (ADR-0009)

Every guest session gets a private copy of the Brassvale branch, provisioned in the same
transaction as the session row.

```
sessions(id, created_at, expires_at, ip_hash, daily_seed, nerve_remaining jsonb)
customers(id, session_id → sessions, display_name, security_question,
          security_answer_hash, security_answer_hint, phone, created_at)
accounts(id, session_id → sessions, customer_id → customers NULL, number,
         kind ['checking','vault','mule','equity'], currency, created_at,
         UNIQUE (session_id, number))
```

Per session: 5 customers with checking accounts, the vault (custodian: Margaret Holloway,
$250,000), the player's `BV-MULE-01`, and `BV-EQUITY-01`, the opening-balance account that
funds everything else through a single journal entry.

A session keeps the `daily_seed` it was created with, so its whole life uses one day's
rotation (`content/daily.yaml`). Every customer gets that day's security question, a bcrypt
hash of their answer, and a `security_answer_hint`: the answer spelled out letter by letter,
which `lookup_account` returns (the Level 3 leak). `phone` is the only column that changes
after provisioning (`update_contact_info`, the Level 4 gap).
The branch carries over from level to level (ADR-0016); only the vault is topped back up to its
opening balance, by a transfer from equity with no attempt, when a session starts a new level.

## Ledger

```
account_balances(account_id PK, kind, balance_cents, version,
                 FK (account_id, kind) → accounts (id, kind))
journal_entries(id, attempt_id NULL, attempt_created_at NULL, description, created_at,
                FK (attempt_id, attempt_created_at) → attempts)
postings(id, entry_id → journal_entries, account_id → accounts,
         amount_cents bigint,          -- signed: debit negative, credit positive, never 0
         created_at)
```

**Invariants, and what enforces them:**

| # | Invariant | Enforced by |
|---|---|---|
| 1 | Every journal entry's postings sum to zero | `CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY DEFERRED`, checked at commit |
| 2 | Every entry has at least two postings | Same deferred trigger, also fired for new entries |
| 3 | `balance_cents` equals the sum of the account's postings | `LedgerService` updates both in one transaction; `LedgerReconciler` re-derives balances from postings (tests now, scheduled job later) |
| 4 | Only `equity` accounts may go negative | `CHECK (kind = 'equity' OR balance_cents >= 0)`; `kind` is pinned to the account by the composite FK |
| 5 | Entries and postings are append-only | `BEFORE UPDATE/DELETE/TRUNCATE` triggers; corrections are new entries |

**Concurrency.** `account_balances.version` is the optimistic lock (JPA `@Version`). A
transfer that loses a race fails at commit and is retried with fresh balances
(`@Retryable`, jittered backoff). Updates are flushed in primary-key order, so two
transfers cannot deadlock. The duplicate `accounts.version` from the first draft was
dropped: account rows never change after creation.

**Tests.** jqwik generates random transfer sequences and compares the real service with
an in-memory model; a concurrency test runs 400 transfers from 16 threads over 4 hot
accounts; raw-SQL tests prove the database rejects violations on its own.

## Reliability tables

```
idempotency_keys(key PK, request_hash, response_json jsonb, created_at)
outbox_events(id, aggregate_type, aggregate_id, event_type, topic, message_key,
              payload jsonb, trace_context jsonb, created_at, published_at NULL)
              -- partial index on unpublished; (topic, message_key) for the staleness fence
processed_events(consumer, event_id, processed_at, PK (consumer, event_id))
```

**Outbox (ADR-0002).** Every event is an `outbox_events` row written in the transaction
of the change it describes; the row id is the event id. `trace_context` holds the writer's
W3C trace context, so the event continues the request's trace when the relay sends it.
Published rows are deleted after a day. A consumer claims `(consumer, event_id)` in
`processed_events` in the same transaction as its update, so a redelivered event is a
no-op. Event payloads: `docs/contracts/events/`.

An idempotency key is written in the same transaction as the transfer's postings, so a key
exists only if its transfer committed. A retry with the same key and request replays the
stored result (`replayed: true`); the same key with a different request is a conflict.
Rejections (insufficient funds) are stored and replayed too.

## Game tables

```
attempts(id, created_at, session_id → sessions, level, combo_id, tiles jsonb, daily_seed,
         outcome ['won','blocked','refused','error'] NULL while in flight, amount_cents,
         cached, trace_id, reply, stop_reason, input_tokens, output_tokens, finished_at,
         CHECK ((outcome IS NULL) = (finished_at IS NULL)), PRIMARY KEY (id, created_at))
         -- PARTITION BY RANGE (created_at), monthly; see ADR-0010
tool_calls(id, attempt_id, attempt_created_at, ordinal, tool, args jsonb,
           policy_decision ['allow','deny'], policy_reason, result jsonb, review jsonb NULL,
           latency_ms, created_at, UNIQUE (attempt_id, ordinal),
           FK (attempt_id, attempt_created_at) → attempts)
leaderboard(session_id PK → sessions, display_alias, score, best_level NULL,
            attempts_used, stolen_cents, levels_cracked, updated_at)  -- Kafka projection
leaderboard_levels(session_id → sessions, level, points, cracked_at,
                   PRIMARY KEY (session_id, level))                -- one row per cracked level
audit_log(id, event_id UNIQUE NULL, actor, action, target, details jsonb, created_at)
account_signals(account_id PK, session_id, teller_credits, teller_credit_cents,
                last_teller_credit_at, updated_at)                -- Kafka projection
llm_usage(day PK, input_tokens, output_tokens, est_cost_micros)  -- budget switch reads this
attempt_cache(level, daily_seed, combo_id, variant, transcript jsonb, created_at,
              PRIMARY KEY (level, daily_seed, combo_id, variant))
```

Every tool call Penny makes is a `tool_calls` row: allowed or denied, valid or malformed,
with the policy engine's reason code and what the tool returned. `review` holds the Level 5
guardrail verdict. `attempt_cache` stores the model's decisions (tool calls and reply), and
a hit replays them through the policy engine and the current session's ledger (ADR-0012).
`variant` is the model id plus a fingerprint of the content files. `llm_usage` counts
micro-dollars, because a Haiku-class attempt costs a fraction of a cent.

**Projections** are kept by Kafka consumers and can be rebuilt from the events, so they
carry no foreign keys into the tables the events came from. Their updates commute (sums,
counts, `greatest()`), so redelivered or reordered events cannot skew them.
`account_signals` feeds the Level 5 velocity rule (ADR-0013). `leaderboard` gets a row on a
session's first finished attempt; `best_level` stays NULL until a win, and only rows with a
win are ranked (score, then `stolen_cents`). A win on a level the session has not cracked yet
inserts its `leaderboard_levels` row (the primary key makes a second crack a no-op) and adds
those points to `score`; the nerve bonus comes from `nerve_left` on `AttemptResolved`. `audit_log` gets one row per event (`event_id` is unique).

## Notes

- Indexes: `postings(account_id)`, `postings(entry_id)`, `outbox_events(created_at) WHERE
  published_at IS NULL`, `outbox_events(topic, message_key)`, `attempts(session_id)`,
  `tool_calls(attempt_id)`, `customers(session_id)`, `sessions(created_at)`,
  `leaderboard(score DESC, stolen_cents DESC) WHERE best_level IS NOT NULL`.
- IP addresses are stored only as HMAC-SHA256 hashes with a secret salt.
- Retention (not implemented yet): drop `attempts` partitions and expired sessions older
  than 90 days. Rows referencing an attempt must be removed first (ADR-0010), and the
  append-only ledger needs an explicit archive step for expired sessions.
